# Reeman - Generator

The generator introspects your database and generates schema files + CRUD routes. Runs as a local tool within the project.

```bash
bun reeman crud all
bun reeman schema authors --force
bun reeman crud countries
bun reeman install ./studio.tar.gz
```

Supports MySQL and SQLite. See [generator/AGENTS.md](AGENTS.md) and [internals/GENERATOR_INTERNALS.md](../internals/GENERATOR_INTERNALS.md#generators) for the full documentation including:

- Common flags (`--force`, `--translate`, `--prefix`, `--parent`, `--pagination`, `--template-tags`)
- reeman menu options and bulk CRUD flow
- Nested CRUD (master-detail)
- Cursor & offset pagination (`--pagination cursor|offset`)
- Form field rendering mode (`--template-tags flat|tags`)
- Tags translation
- Column comment-driven field types
- Fulltext search
- Currency field rendering
- Placeholder naming convention
- `config/db_structure.ts` constants reference
- URL Localization via `route_name` keys

## Generated folder structure

```
apps/main/<table>/
├-- schema/                  # Generated by `bun reeman schema`
│   ├-- table.generated.ts   # Auto-generated (safe to overwrite)
│   ├-- table.ts             # User-editable, created once (never overwritten)
│   └-- validation_server.ts # Auto-generated Zod validation (safe to overwrite)
├-- {locale}.json            # Co-located UI translations, one file per locale (see below)
├-- index.ts                 # CRUD route handlers (generated by `bun reeman crud`)
├-- sql.ts                   # SQL query functions (generated by `bun reeman crud`)
├-- sql_view.ts              # View-based queries, if a view exists (generated by `bun reeman crud`)
├-- form.ree                 # Create/edit form template (generated by `bun reeman crud`)
└-- index.ree                # List/index template (generated by `bun reeman crud`)
```

## Nested child structure

When `--parent <table>` is specified, the child is placed directly under the parent's directory with a minimal file set:

```
apps/main/<parent>/
  <child>/
    index.ts           # Only create, edit, edit-data (JSON), validate
    sql.ts             # Scoped queries: all accept parent_id, filter by FK
    schema/
      table.ts         # Field definitions + parent export
      table.generated.ts
      validation_server.ts
    {locale}.json            # Co-located UI translations (synced by sync-translations)
```

The child has **no `form.ree` or `index.ree`** - the form UI lives in the parent's `form.ree` inside `<!-- GEN:CHILDREN:START -->` markers.

### Examples

```sh
# Generate parent (standalone CRUD)
bun reeman crud equipment

# Generate child nested under parent
bun reeman crud equipment_items --parent equipment

# With prefix
bun reeman crud equipment_items --parent equipment --prefix admin

# Refresh a child (preserves --parent)
bun reeman refresh-crud equipment_items --parent equipment --mode fields
```

## Sync Translations

Co-located `{locale}.json` files are the source of truth. To add or change translations:

- edit the namespace JSON file directly
- `bun reeman sync-translations --translate` - AI-powered sync across namespace files
- `/translations` admin UI in the reeman app - manual editing through the app

```bash
bun reeman sync-translations --translate   # translate missing keys via the configured AI provider
```

Locales are full BCP 47 identifiers configured in `config/supported_locales.ts`. Add one with `bun reeman add-locale <locale_code> [--translate]`, for example `bun reeman add-locale de-at --translate`.

After sync, the server's `POST /__reload-translations` endpoint (called by the generator) refreshes in-memory translation maps on the running server.

## DDL Cache

The generator uses a **DDL cache** (`generator/ddl_cache.ts`) to avoid repeated database introspection within a single run. Each entry point introspects the full database schema once at startup, detects foreign key relationships (native DDL, implicit `*_id` naming, and view JOIN patterns), and holds the result in memory. Every downstream reader in that run shares the one snapshot instead of re-querying.

The cache is **in-memory only and per-process** - there is deliberately no on-disk cache. Schema changes are normally made outside the generators (direct `mysql`/`sqlite3` calls, migration tools), so a cache surviving process exit would hand generation a schema the database no longer has. Every entry point re-introspects: interactive reeman at startup, the `schema`/`crud`/`bulk`/`refresh-crud` subcommands, and the MCP server's generator tools.

There is no manual rescan command - it would be redundant. To discard the snapshot mid-process (e.g. from a long-running MCP server), call `invalidate_cache()` from `generator/ddl_cache`; the next `load_ddl_cache()` re-introspects.

## Auto-formatting

The CRUD generator runs `reettier` on the generated route directory automatically after all files are written.
